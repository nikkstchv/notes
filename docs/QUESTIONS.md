# Ответы на вопросы

## Где должна находиться проверка владельца заметки: в контроллере, сервисе или репозитории? Почему?

В **сервисе**. Это инвариант домена: «менять можно только свою заметку». Контроллер только достаёт `userId` из auth-контекста и вызывает сервис. Если проверку оставить в контроллере, её легко забыть на следующем эндпоинте (`GET`, `DELETE`, админский скрипт, очередь).

Репозиторий / Prisma-вызов **участвует** в проверке технически: в `where` всегда передаются и `id`, и `userId`. Но решение «это чужая заметка → для клиента её нет» принимает сервис: он мапит `P2025` в `NoteNotFoundError`. Репозиторий не должен знать про HTTP.

## Как избежать ситуации, когда пользователь меняет чужую заметку?

Несколько слоёв, без одного из них дыра возвращается:

1. `userId` только из сессии/JWT, никогда из body или query.
2. Один запрос на изменение: `UPDATE ... WHERE id = :noteId AND userId = :userId`. Сначала `find`, потом `update` по одному `id` – гонка и лишний шанс забыть фильтр.
3. В `data` попадают только `title` и `content`. Подменить `userId` через PATCH нельзя.
4. Контроллер не принимает «заметку целиком» от клиента и не делает `prisma.note.update({ where: { id } })`.

## Какой HTTP-статус лучше вернуть при попытке открыть чужую заметку?

**404 Not Found**, тот же, что для несуществующего id.

`403 Forbidden` честно говорит: «запись есть, просто не твоя». По UUID тогда можно перебирать чужие заметки. Для приватного ресурса «своя / ничья» достаточно; факт чужого владения клиенту не нужен.

`401` здесь не подходит: пользователь уже авторизован, просто просит чужой объект.

## Какие поля разрешено изменять пользователю?

Только **`title`** и **`content`**.

Нельзя:

- `id` – идентификатор задаёт система
- `userId` – иначе заметку можно «перевесить» на себя или на другого
- `createdAt` – факт создания
- `updatedAt` – ставит PostgreSQL / Prisma `@updatedAt`

## Нужна ли транзакция при обновлении одной заметки?

**Нет.** Один `UPDATE` в PostgreSQL атомарный: либо строка изменилась, либо нет.

Транзакция понадобится, если в одном действии трогаем несколько записей: теги, аудит, outbox, инвалидация связанного агрегата. Для текущего `updateNote` это лишняя сложность.

## Какие индексы стоит добавить в PostgreSQL?

- PK по `Note.id` – точечное чтение/изменение/удаление.
- Индекс по `userId` – все запросы изолированы по владельцу, плюс FK на `User`.
- Составной `(userId, createdAt, id)` – список своих заметок с сортировкой и cursor-пагинацией без filesort.

Отдельный индекс только по `createdAt` для этого модуля не нужен: глобальной ленты нет. Уникальность `(id, userId)` тоже не нужна: `id` уже уникален.

На практике составной индекс с префиксом `userId` закрывает и выборку «все заметки пользователя», так что узкий `@@index([userId])` можно не дублировать, если смотреть `EXPLAIN`. В схеме оба индекса оставлены явно, как страховка под FK и под список.

## Что изменится, если заметок у пользователя будет несколько миллионов?

- Список **только** с пагинацией (cursor, жёсткий `limit`). `findMany` без лимита положит API и память.
- Список обязан ходить в составной индекс, не сортировать миллионы в памяти.
- Не отдавать и не кешировать «все заметки пользователя» одним ключом Redis.
- `updatedAt` в курсоре хуже `createdAt`: правки прыгают по страницам; для ленты стабильнее время создания + `id`.
- Если горячий пользователь пишет очень часто – партиционирование по времени или шардирование по `userId`, но это уже следующий порядок масштаба, не стартовая схема.

## Как бы вы добавили кеширование через Redis?

Точечно, с короткой жизнью и явной инвалидацией.

- Ключ заметки: `note:{id}` → JSON. После чтения **обязательно** сравнить `userId` с текущим пользователем; чужой ключ не отдавать (и лучше не писать в кеш ответ 404).
- TTL 30–60 секунд, чтобы промах инвалидации не держал вечный stale.
- На `PATCH` / `DELETE` – `DEL note:{id}`. На `POST` список и так неполный, отдельный ключ одной заметки ещё не нужен.
- Список `notes:user:{userId}:limit:{n}:cursor:{c}` кешировать опасно: комбинаций много, инвалидация на каждую запись раздувается. Имеет смысл разве что первую страницу `notes:user:{userId}:first`, и тоже сбрасывать на любой write этого пользователя.

Кеш – дополнение к БД, не источник прав доступа.

## В каких случаях здесь мог бы пригодиться Socket.IO?

CRUD из одной вкладки в Socket.IO не нуждается.

Имеет смысл, когда одно и то же состояние должно доехать без перезагрузки:

- пользователь открыл заметку на телефоне и на ноутбуке – правка на одном устройстве сразу видна на другом;
- позже – совместное редактирование (presence, курсоры, конфликты);
- уведомление «заметку удалили на другом клиенте», чтобы UI не показывал призрак.

Комнаты резать по `userId` (и при коллаборации – по `noteId` после проверки владельца). Рассылать события чужим пользователям нельзя.

## Какие части решения вы бы покрыли тестами в первую очередь?

Сначала инварианты безопасности и контракт `updateNote` – здесь цена бага максимальна:

1. Своя заметка обновляется, `title`/`content` меняются, `updatedAt` растёт.
2. Чужой `noteId` → `NoteNotFoundError` (404), строка в БД не меняется.
3. Несуществующий `noteId` → тот же `NoteNotFoundError`.
4. В payload есть `userId` / `id` – они не попадают в `UPDATE`.
5. Пустой `title` или пустой PATCH → `NoteValidationError` (400).
6. Частичный PATCH: передали только `content`, `title` не затирается.

После этого – список только своих заметок и cursor (не отдаём лишнюю страницу, не смешиваем пользователей). Контроллер/JWT – позже: без сервисных тестов на владельца HTTP-обвязка мало что гарантирует.
